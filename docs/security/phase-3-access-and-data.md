# Phase 3 access and data notes`n`n## Data present in Phase 3`n`n| Data | Purpose | Access | Current storage |`n| --- | --- | --- | --- |`n| Email address and verification timestamp | Passwordless sign-in and account recovery path | Account owner; admin lookup is by explicit request | PostgreSQL users table |`n| OTP digest, expiry, attempt count | Verify email sign-in | API only | PostgreSQL; HMAC digest uses `AUTH_OTP_PEPPER` |`n| Session and CSRF token digests | Authenticate requests and enforce CSRF | API only | PostgreSQL; browser receives opaque cookies |`n| TOTP secret ciphertext and MFA state | Require MFA for privileged roles | API decrypts with dedicated key; owner uses authenticator | PostgreSQL encrypted with AES-GCM and `MFA_ENCRYPTION_KEY_B64` |`n| Role grants | Authorize applicant, staff, and administrator workflows | API; admins can manage other users | PostgreSQL |`n| Case cycle key, status, owner, staff assignment, revision | Track preparation workflow shell | Owner, assigned staff, or administrator per matrix | PostgreSQL |`n| Case events and audit events | Explain sensitive access and changes | Case participants; audit is server-side | PostgreSQL append-only triggers |`n`nThe app does not yet store DV-form answers, family-member details, photos, payment evidence, confirmation numbers, government account credentials, support messages, or official application submission data. Retention durations and automated deletion are not implemented; approve policy before real account/case use.`n`n## Access matrix`n`n| Action/resource | Anonymous | Applicant | Staff (MFA) | Administrator (MFA) |`n| --- | --- | --- | --- | --- |`n| Request/verify sign-in code | Own email flow | Yes | Yes | Yes |`n| View own session / logout | No | Yes | Yes | Yes |`n| Create/list own cases | No | Yes | Only if also applicant | Yes, for own cases |`n| Read case details/timeline | No | Own cases only | Assigned cases only | All cases |`n| View staff case queue | No | No | Assigned cases only | All cases |`n| Change case status | No | No | Assigned cases only | All cases |`n| Assign a case | No | No | No | Active MFA-enabled staff only |`n| List staff users / lookup account | No | No | No | Yes; lookup uses POST body |`n| Grant/revoke staff or admin role | No | No | No | Yes; not self; final admin protected |`n| Reset another user's MFA | No | No | No | Yes; sessions revoked |`n`nAll ownership and role rules are enforced in the API. Hiding a UI control is not an access control. Unknown and unowned case identifiers return the same not-found shape. The API emits request IDs and logs operation plus a generic failure class; it avoids logging raw database/SMTP errors that might contain personal values.`n`n## Controls and limitations`n`n- The CI PostgreSQL integration job exercises applicant ownership, staff assignment scoping and MFA gating, case-read audit outcomes, concurrent status revisions, and logout revocation. Those checks require the disposable PostgreSQL service; a local `go test ./...` without `DATABASE_URL` reports the integration tests as skipped.`n`n- Passwordless challenge codes: 10-minute expiry, bounded attempts, HMAC digest, generic response, and process-local IP/email rate limit.`n- Sessions: opaque random token stored only as a digest, `HttpOnly` cookie, expiry, CSRF cookie/header pair, origin check, and logout revocation.`n- Staff/admin access requires TOTP MFA. TOTP secrets are encrypted at rest with a separate 32-byte key. Current recovery is admin reset; there are no backup codes.`n- Sensitive state changes and case views create append-only case/audit records. PostgreSQL's table owner can bypass triggers; production should use separate migration and runtime roles, and runtime must not own tables.`n- The API's in-memory limiter is per process and resets at restart. It is not sufficient for a multi-instance public deployment.`n- Email delivery uses SMTP with STARTTLS; production startup requires database, HTTPS public origin, and valid SMTP configuration. Delivery retry/outbox and monitoring are not implemented.`n- `GET /healthz` is a process health check, not a dependency readiness check.`n- Phase 3 does not meet a real-data launch gate until PostgreSQL integration, restore, access-isolation, MFA, privacy, retention, and operational checks are completed.`n
